# gridfm-anomaly

IMT4392 (NTNU) course project: anomaly detection on the electric power grid using GridFM foundation models.
Course paper: "Foundation Models for the Electric Power Grid" (Hamann et al., arXiv 2407.09434, 2024, a position paper).
The checkpoints used here come from **GENCO** (Puech et al., arXiv 2608.09921, 2026). Citations are in
`results/dataset_overview.md` §5.

**Status:** setup, first inference and data exploration done (stage 1 groundwork). No fine-tuning or anomaly
detector yet. Every command and version is in [`SETUP_LOG.md`](SETUP_LOG.md).

## Recreate the environment (Windows, CPU)

Python **3.11**: gridfm-datakit does not support 3.12 on Windows, and neither package supports 3.13. torch is pinned
to **2.12.0+cpu** because prebuilt `torch-scatter` wheels for Windows exist only up to torch 2.12.

```bash
py -3.11 -m venv venv
./venv/Scripts/python.exe -m pip install --upgrade pip
./venv/Scripts/python.exe -m pip install -r requirements.txt \
    --extra-index-url https://download.pytorch.org/whl/cpu \
    -f https://data.pyg.org/whl/torch-2.12.0+cpu.html
```

Key versions: gridfm-graphkit 0.9.0.3, gridfm-datakit 1.1.0, torch 2.12.0+cpu, torch_geometric 2.8.0, mlflow 3.16.1.
graphkit logs to a local `./mlruns` folder, which MLflow 3.16 refuses unless `MLFLOW_ALLOW_FILE_STORE=true` is set
(`run_inference.py` sets it itself; set it yourself when calling the CLI directly).

## Get the model and data (~1 GB)

```bash
./venv/Scripts/hf.exe download gridfm/genco-pf-datakit \
    --include "case14_ieee/base/seed0/*" --include "case14_ieee/tiny/seed0/*" \
    --include "mlflow/eval/case14_ieee/*/seed0/*/artifacts/test/*.csv" \
    --include "mlflow/eval/case14_ieee/base/seed0/*/artifacts/stats/*" --local-dir checkpoints/genco-pf-datakit
./venv/Scripts/hf.exe download gridfm/pf_small_case14_ieee --repo-type dataset --local-dir data/case14_ieee/raw
./venv/Scripts/hf.exe download pfdelta/pfdelta case14.tar.gz shuffle_files.tar.gz --repo-type dataset --local-dir data/pfdelta_orig
```
(With the `hf` CLI, repeat `--include` for every pattern.) Extracting `case14.tar.gz` is optional: the scripts read it
in place, and extraction takes ~25 min on Windows.

## Findings

### What worked
- **Environment on native Windows/CPU**, after two fixes: Python 3.11 and torch 2.12 for prebuilt `torch-scatter`.
  Inference on 1000 case14 samples takes ~40 s on CPU. No GPU needed (the machine's AMD GPU isn't usable by PyTorch on Windows).
- **The GENCO case14 checkpoint loads strictly in graphkit 0.9.0.3** (0 missing / unexpected keys). Feature order,
  masking and normalizer are unchanged from the 0.0.7-based training branch.
- **Reproduction matches the model card**: Qg and slack Vm RMSE within ±5 %. Va, PQ Vm and slack Pg are 25–35 % *lower*
  on our 1000 samples, because the errors are heavy-tailed and the card's 22k test set has more tail (median errors are
  7–20× below RMSE).
- **Predict-then-check is a strong baseline** on in-distribution data: overload precision/recall 1.00/1.00. Voltage
  1.00/0.96 once the slack voltage setpoint is treated as known. graphkit's `thermal_excess` maps exactly onto `y_overload`.
- **Embeddings are informative**: 384-d per bus. In a 2-D PCA of the mean-pooled embeddings, overload samples form a
  separate arm (PC1 alone: AUC 1.00 for `y_overload`, vs 0.51 for total load).

### What did not work / needed workarounds
- `gridfm/gridfm-pf-reconstruction` does not exist publicly. The case14 PF model is `gridfm/genco-pf-datakit` (GENCO).
- The `gridfm/pfdelta_task*` datasets are **case118-only**. case14 PFΔ comes from the original release (`pfdelta/pfdelta`)
  and still needs converting (datakit repo's `pfdelta/batch_convert_pfdelta.py`, not in the pip package, plus a small
  wrapper for near-infeasible files).
- The checkpoint config is "v0". It needs `--config_conversion auto_inline` (the scripts do this).
- MLflow file-store refusal, DDP chosen on CPU with `accelerator: auto`, a Windows console encoding crash: all fixed
  and logged in `SETUP_LOG.md`.
- **Deferred:** the datakit/Julia N-k generation smoke test (`gridfm_datakit setup_pm` not run). PFΔ covers our data needs.

### Surprises
1. **The checkpoint's case14 data has no N-0 at all.** Every one of the 219,606 scenarios is N-1 (82 % branch, 18 %
   generator outages). N-0 vs N-1 comparisons need PFΔ.
2. **graphkit hides the slack bus Vm** (and keeps Va), unlike the textbook PF setup. The true slack Vm sits exactly on the
   1.06 limit in 99 % of samples, so a naive predict-then-check flags 415 of 1000 samples as over-voltage (precision 0.06).
3. **The two data sources behave oppositely.** datakit case14 is mild (7 % abnormal, mostly *over*-voltage). PFΔ case14
   is heavily stressed (66 % abnormal, mostly *under*-voltage down to 0.48 p.u.). In PFΔ, **N-0 is the most stressed
   topology** (20 % normal vs 59 % for N-1), so topology and load level are confounded.
4. **Hard ≠ anomalous.** The 5 % highest-error samples are mostly branch outages, with the largest errors at the slack
   bus. But they are no more likely to contain a violation than average (7/50 vs 6.4 %). Reconstruction error correlates
   only weakly with the labels (Spearman ≤ 0.12).
5. One sample (438, outage of the 472 MVA slack line 0–1) has 3.6× the error of any other and sets most maxima.
6. Reactive-power limits are violated in 57 % of datakit scenarios (PF does not enforce them), so they are useless as an anomaly class.

### Open questions to resolve before the next step
- **Islanding as a class: not possible with the current data.** Both PFΔ (resamples until the graph is connected) and
  datakit (`check_single_connected_component`) reject islanded topologies. Branch 13 (bus 6–7) is never outaged in
  datakit because bus 7 would island. An islanding class would need modified generators and a PF with one slack per
  island. **Decide: drop it, or treat "outage that would island" as a topology-only rule outside the model.**
- **N-k labeling: yes, feasible.** PFΔ stores `vm`, `vmin/vmax`, branch flows, `rate_a` and outage flags per sample. Multi-label
  targets `y_voltage`, `y_overload` (normal = neither) can be computed for all 105k feasible samples (counts in
  `results/data_format.md` §5). Open: labeling rule for near-infeasible (nose) samples (separate class or excluded?),
  and the PFΔ load-level confound when comparing N-0/N-1/N-2.
- **Embeddings: usable, with a caveat.** They separate overloads cleanly and voltage violations partly, but much of the
  voltage separation is load level. And on data where the model is accurate, an embedding classifier may just relearn
  predict-then-check. **The real test is PFΔ N-2 and near-infeasible data, where the state prediction degrades.**
- **Slack voltage handling**: for approach A and the predict-then-check baseline, use the slack setpoint as known
  (graphkit masks it by convention). Decide whether to also unmask it during fine-tuning.
- **PFΔ split plan** (not run yet): fine-tune on N-0/N-1 feasible (+ optionally near-infeasible train) outside PFΔ's
  fixed test positions (last 2,000 of each shuffled list). **All N-2 strictly held out** as the final test set. Pick
  Stage-2 hard cases from ≤ 1000 training-pool samples, not test positions. Details in `results/inference_summary.md`.
- **Zero-shot cross-topology test**: case30/57/118/500 checkpoints exist (same weight size, so they run on any grid).
  Decide which normalizer (`baseMVA`) to use when running a case30 model on case14.
- Which training data for the classifier: PFΔ (balanced, stressed) vs datakit (realistic base rates, ~94 % normal), or both.
